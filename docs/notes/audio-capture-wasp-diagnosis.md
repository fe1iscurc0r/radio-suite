# WASAPI 麦克风采集：样本预算"缺失"其实是首帧启动延迟（2026-10-25 初诊，2026-10-30 定案）

## 现象

本机（Realtek 麦克风阵列，RtAudio device id=130）用 `audio-in-smoke` 采集 2 秒：

```
captured 2s -> 60 frames (28.5 fps, 期望 50) peak=548
sample budget: 57600 / 100890 (57.1%)
```

即"拿到的样本只有理论预算的 ~57%"，一度被判定为 RtAudio 共享模式丢样。

## 定案（2026-10-30 实测）

**没有稳态丢样，缺的是设备启动时间。** 带时间戳的探针实测（同一台机器、同一个
Realtek 麦克风 id=130，48kHz/16bit/mono）：

| 观察量 | 实测 |
|---|---|
| 首个采集回调到达时刻 | **0.44 ~ 0.51 s**（多次运行） |
| 首帧之后的帧间隔 | **20.0 ms 恒定**（50.0 fps） |
| 稳态样本预算（预热 1 s 后测 2 s） | **100.1%**（111 帧 / 2.20 s） |
| 含启动段的整段预算（6 s 窗口） | 91.3% |
| 含启动段的整段预算（15 s 窗口） | 97.0% |

`2 s 窗口 57%`、`6 s 窗口 91%`、`15 s 窗口 97%` 与"固定丢掉 ~0.48 s"完全吻合：
`(2 − 0.48)/2 = 76%`、`(6 − 0.48)/6 = 92%`、`(15 − 0.48)/15 = 97%`。旧测量把
`start()` 到首回调之间的墙钟时间算成了"应该是样本却没拿到"，于是短窗口看起来像
大面积丢样。

启动开销来自 WASAPI 共享模式的流初始化：`InitializeSharedAudioStream`
（IAudioClient3）+ `Start()` + 等引擎出第一个周期，本身就要几百毫秒。这是**一次性**
成本，不随采集时长累积，也不影响采样率（帧间隔恒定 20.0 ms，无重采样失真）。

## 已排除的假设（初诊时成立，仍然有效）

1. **不是设备原生速率不匹配**：`preferredSampleRate` 与 `getStreamSampleRate()`
   均为 48000；按原生速率开流 + 回调内线性重采样反而更差（预算 45.8%），已回滚。
2. **不是缓冲粒度**：`buffer_frames=480`（10 ms）下同样表现。
3. **不是回调丢帧**：回调内样本数正常（每帧 960），`AudioIn::overflows()` 全程 0。

## 影响

| 用途 | 影响 | 说明 |
|---|---|---|
| 语音发射 / Voice Memory 录音 | 每次开始采集后前 ~0.5 s 无数据 | 语音类用途可忽略；录音上限已按样本数计（见下），不会提前截断 |
| SSTV 发送 | 无 | 走 AudioOut 播放链，不经采集路径 |
| 通话（PTT 语音上行） | 按下 PTT 后首 ~0.5 s 静音 | 若在意，可在 `AudioIn::start()` 返回后做一次短预热再开门禁 |

## 已落地的补救（仍然保留）

`apps/desktop/app/voice_memory.cpp`：

- 录音上限按样本数：`rec_pcm_.size() >= kRate * kMaxSeconds`（48 000 × 60），
  不用墙钟计时——避免任何"起始静音"被算进录音时长。
- 时长显示按样本数折算：`rec_pcm_.size() / double(kRate)`，与文件内容一致。

这两条与本次定案不冲突：它们防的是"把启动静音算成内容"，本身即正确做法。

## 复现命令

```bash
cd build/apps/desktop/audio && audio-in-smoke.exe
# 输出首帧延迟、预热丢帧数、稳态 fps 与样本预算；退出码 0 = 达标
```

工具的量法：先等首帧（最多 3 s），从首帧起丢 1 s 预热，再测约 2 s 稳态。
失败条件：无回调 / 稳态帧率超出 40–60 fps / 样本预算低于 88%。

## 不再需要做的事

- ~~WASAPI 独占模式~~、~~IAudioClient 直连重写~~：稳态本来就不丢样，为这 0.5 s
  启动开销重写采集层不划算。
- 若将来真的需要"按下即有声"，在会话层做预热（开 PTT 前先 `start()` 并丢弃首
  0.5 s）即可，不必动音频后端。
